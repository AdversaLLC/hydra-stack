# hashdeep (Bulk Hash Verification & Auditing)

`hashdeep` (and its predecessor `md5deep`) computes hashes recursively across many files at once and supports comparing results against a previously generated hash list — useful for verifying a large evidence export hasn't changed, or checking a file set against a known-file/known-bad hash database.

## Core operations

1. **Generate a hash list**: `hashdeep -r -c md5,sha256 <directory>` (verify exact flag syntax against `hashdeep -h`) recursively hashes every file, output in a machine-readable format that can be saved for later comparison.
2. **Audit mode** — compare a directory against a previously saved hash list to detect additions, deletions, or modifications: general pattern `hashdeep -r -a -k <baseline-hashlist> <directory>` (again, verify exact flags — audit-mode syntax has specific requirements around the baseline file format that should be confirmed against current documentation rather than assumed).
3. **Matching against a known hash set** (e.g., a NIST NSRL-style known-good/known-bad list) to quickly flag files that match or don't match: general pattern uses `-m` (match) or `-x` (negative match/exclude known) style flags — confirm exact behavior before use, since match-mode semantics (match vs. exclude) are easy to invert by mistake.

## Workflow

1. Confirm the source directory/files are a copy or read-only-mounted evidence, not being modified as part of another concurrent operation.
2. Generate the hash list, saving output to a file on separate media from the evidence.
3. For audit/comparison runs, clearly label which hash list is the "baseline" (earlier, trusted state) and which directory is being checked against it — don't let this get inverted, since it changes the meaning of "added" vs. "removed" in the output.
4. Record the exact command and the full output (or its location) for the report — never summarize an audit result ("no changes detected") without having actually seen the tool's output confirm that.

## What this skill must never do automatically

- Modify, move, or delete any file based on hashdeep output without separate explicit instruction — hashdeep itself is read-only, but don't chain it into destructive follow-up actions automatically.
- Report a "no changes" or "all matched" result without having actually run the comparison and observed that output.
- Confuse baseline and comparison directories, or report the audit direction backwards.

## Troubleshooting

| Symptom | Likely cause | Steps |
|---|---|---|
| Audit reports everything as "unmatched" that should match | Baseline hash list uses a different algorithm set than the current run, or was generated with different path/filename conventions | Confirm both runs used the same `-c` algorithm list; check whether audit mode compares by hash-only or also by filename/path |
| Extremely slow on large trees | Large file counts/sizes with multiple hash algorithms computed simultaneously | Consider narrowing algorithm selection (e.g., SHA-256 only) if MD5+SHA-1+SHA-256 all at once isn't needed for the case |
| Hash list file won't load in audit mode | Format mismatch (hashdeep's own format vs. plain md5sum-style lists) | Confirm the baseline file was generated by hashdeep itself in a compatible format, not a different hashing tool's output format |

## Handoff

- Whole-device/image acquisition hashing → `paladin-forensic-workflow`, `dc3dd`, `dcfldd`, `ewf-tools`.
- Writing up verification results in a report → `forensic-reporting`.
